## 中文

`v0.5.1` 是一个稳定化补丁版本。它打包 `v0.5.0` 之后已经合入 `main` 的公开变更，重点是
记忆治理加固、公开写入授权边界澄清、测试能力基础和 release validator thin-entrypoint closeout。

### 主要变更

- 记忆治理加固：明确项目记忆模板治理指南、收拢命令索引启动引导、在阶段收尾门禁中集成
  memory diagnosis、设计结构化记忆诊断方案、新增已完成列表增长检测和记忆升级中稳定笔记
  保留修复。（#157 / PR #157，#159 / PR #159，#160 / PR #160，#161 / PR #161，
  #162 / PR #162，#163 / PR #163，#164 / PR #164）
- 公开写入授权边界：澄清 public-safe write authorization boundaries，把跨仓库写入范围
  要求和授权检查明确记录到公共治理文档中。（#170 / PR #173）
- 测试能力基础：新增 TDD 和测试策略知识模式、项目 agent 测试工作流命令卡、测试约定上下文条目
  和 workflow-spec-lite 测试指引，为后续完整测试能力覆盖建立首个切片。（#168 / PR #174）
- Release validator thin-entrypoint：把 `scripts/validate-release.ps1` 从 2,496 行
  重构为 566 行主入口，提取 10 个验证 helper 模块；完成 Phase 1-5 closeout 并记录最终
  结构、增长规则和 acceptance mapping。（#175 / PR #176 / PR #177 / PR #178 / PR #179 /

## English

`v0.5.1` is a stabilization patch release. It packages public changes already
merged to `main` after `v0.5.0`, focused on memory governance hardening,
public-safe write authorization boundary clarification, testing capability
foundations, and the release validator thin-entrypoint closeout.

### Highlights

- Memory governance hardening: clarified project memory template governance,
  aligned commands index startup guidance, integrated memory diagnosis into the
  phase-close gate, defined structural memory diagnostics design, added
  completed-list growth detection, and fixed stable notes preservation during
  memory upgrade. (#157 / PR #157, #159 / PR #159, #160 / PR #160,
  #161 / PR #161, #162 / PR #162, #163 / PR #163, #164 / PR #164)
- Public-safe write authorization boundaries: clarified cross-repository write
  scope requirements and authorization checks in public governance
  documentation. (#170 / PR #173)
- Testing capability foundations: added TDD and test-strategy knowledge
  patterns, project-agent test workflow command cards, testing convention
  context entries, and workflow-spec-lite test guidance, establishing the first
  slice toward full testing capability coverage. (#168 / PR #174)
- Release validator thin-entrypoint: refactored `scripts/validate-release.ps1`
  from 2,496 lines to a 566-line main entrypoint, extracted 10 validation
  helper modules; completed Phase 1-5 closeout with documented final structure,
  growth rules, and acceptance mapping. (#175 / PR #176 / PR #177 / PR #178 /
  PR #179 / PR #180)

### Validation

- Pre-publication local release validation passed:
  `PASS=62 FAIL=0 WARN=0 DEFERRED=0`.
- `v0.5.1` publish-finalization validation uses:
  `pwsh -NoProfile -File scripts/validate-release.ps1 -TargetVersion v0.5.1`.
- After hosted Release validation, PR base guard, and PR identity guard pass on
  the publish-finalization PR, the maintainer can tag and publish directly from
  the merged `main` commit.

### Upgrade / Usage Impact

- Existing installations do not need a forced migration.
- `minimal`, `recommended`, `full`, and `dev` profile behavior is unchanged.
- The release validator output contract is preserved (62 checks, relative
  ordering, summary shape, and JSON evidence); the internal implementation has
  been modularized into 10 helper modules.
- New testing knowledge patterns, command cards, and context entries are
  knowledge-layer enhancements that do not change the core installed runtime
  workflow.

### Known Limitations

- #165 agentskills.io alignment, #166 eval-driven iteration, #167 knowledge
  lifecycle management, and #169 workflow-spec-lite enhancement remain accepted
  open proposals and are out of scope for this release.
- #132, the runtime state bridge proposal, remains a long-term open proposal and
  is not a blocker for this release.
- #168 testing capability only completes foundations / first slice; full testing
  capability coverage requires a future release.
- This release does not add public domain packs, change install profile
  behavior, add Bash / Zsh wrappers, or modify repository settings, rulesets, or
  secrets.

### Risk / Rollback

- Risk is concentrated in documentation and release validator modularization
  maintainability; user-runtime compatibility risk is low.
- If validation helper modules need adjustment, maintainers can reorganize
  module boundaries through a follow-up governance PR.
- If release text needs correction, maintainers can make a body-only GitHub
  Release edit or synchronize the release notes through a follow-up docs PR.
