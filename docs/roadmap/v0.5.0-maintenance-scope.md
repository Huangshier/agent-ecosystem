# v0.5.0 Maintenance Scope

Status: planning — stabilization-first before expansion.

This document defines the v0.5.0 maintenance sequence for the public
`agent-ecosystem` repository. It answers issue #120 and establishes a
maintenance-first ordering unless the maintainer explicitly chooses expansion.

## Guiding Principle

v0.5.0 should reduce future support cost before adding public domain packs,
new install profiles, or more command surfaces. Stabilization comes first;
expansion follows only after the maintainer authorizes it.

## Suggested PR Order

The suggested implementation order follows the dependency graph and
prioritizes unblocking downstream work.

### PR 1 — Command Boundaries (#119)

- Define `bootstrap_project.ps1` intended responsibilities:
  scaffold creation, safe refresh, force reset.
- Document whether it should continue wrapping memory upgrade and language
  migration, or whether those should become dedicated helpers.
- Decide where old-release upgrade orchestration should live.
- Issue is accepted; no maintainer decision gate remains.
- Validation: `git diff --check` and full release validator.

### PR 2 — Agent Brief (#117, independent of PR 1)

- Add optional `-Brief` output mode to `context_gate.ps1`.
- Preserve existing default output and `-Json` behavior.
- Keep `-Brief` scoped to context reconstruction: project root, git state,
  hot/warm/cold context, active work package, warnings, and next loading step.
- Do not turn `-Brief` into an intent-driven task prompt generator, issue/PR
  handoff generator, priority selector, or write-authorization surface.
- Issue is accepted; small, self-contained enhancement.
- Validation: `git diff --check`, brief-mode smoke test, and full release
  validator.

### PR 3 — Helper Consolidation (#97, after maintainer decision)

- Document authoritative helper ownership model for `Join-PathParts`.
- Reduce duplicates where standalone packaging allows.
- Clarify `knowledge-hub/scripts/` and `project-bootstrap/scripts/` ownership.
- Requires maintainer triage decision before implementation.
- Validation: `git diff --check`, duplicate scan, and full release validator.

### PR 4 — Validator Modularization (#96, after #97 lands)

- Extract shared read-only helpers from `validate-release.ps1`.
- Move check groups behind stable function boundaries.
- Split language migration mode handlers after baseline helpers are stable.
- Each sub-PR must be behavior-preserving and keep full release validation
  passing.
- Requires maintainer triage decision before implementation.
- Validation: `git diff --check` and full release validator after each
  sub-PR.

### PR 5 — Old-Release Upgrade Path (#118, after #119; optionally after #96)

- Define old-release upgrade support matrix.
- Rehearse at least one real tag-to-current path.
- Cover runtime install state and project memory state.
- Requires maintainer triage decision before implementation.
- May land after PR 1 alone, or wait for PR 4 if modularized validator
  fixtures are preferred for the upgrade rehearsal.
- Validation: `git diff --check` and full release validator.

## Explicitly Deferred (unless maintainer chooses otherwise)

The following are out of scope for v0.5.0 unless the maintainer explicitly
authorizes expansion:

- **Domain pack expansion**: no new public domain packs beyond the existing
  `embedded-core` scaffold.
- **Profile expansion**: `full` and `dev` install profiles remain reserved;
  they install the same content as `recommended` until a governance-approved
  expansion lands.
- **Bash/Zsh wrappers**: the public Workflow Kernel remains PowerShell-first.
  Thin cross-platform launchers are deferred.
- **Online auto-updater**: no automatic update mechanism.
- **New agent runtime integration files**: no `CLAUDE.md`, `GEMINI.md`, or
  `.clinerules` generation in templates.
- **Issue #23 expansion roadmap**: closed #23 remains a reference for future
  domain-pack and profile expansion, but it does not drive v0.5.0 sequencing.

## Non-Goals (from #120)

- Do not implement the referenced issues in this planning document.
- Do not add public domain packs, change `full` / `dev` profile behavior,
  or ship Bash/Zsh wrappers here.
- Do not create a release tag or release-prep PR from this document alone.
- Do not duplicate #23's broader expansion roadmap; this document is for
  maintenance sequencing.
