# v0.5.0 Validator Modularization Plan

Status: planning boundary for issue #96.

This plan defines the scoped refactor sequence for the release validator,
workflow-spec-lite validator fixtures, and project-bootstrap language migration
helper. The first PR is documentation-only and behavior-preserving. It records
review boundaries before any large script is split.

## Current Risk

The current maintenance surfaces are large enough that future changes are hard
to review safely:

- `scripts/validate-release.ps1` is about 3,885 lines. Many release checks are
  top-level `try` blocks, with only a small number of local functions around
  installer, runtime smoke, language migration, and language-template fixtures.
- `skills/project-bootstrap/scripts/language_migration.ps1` is about 2,016
  lines. It has helper functions for analysis, backup, apply, validation, and
  narrative migration, but the command-mode dispatch still ties all modes
  together at the script entrypoint.
- `skills/workflow-spec-lite/scripts/validate_spec.ps1` is intentionally small,
  but the release validator embeds large positive and negative validator
  fixtures directly in the release-validation script.

The main review risk is not failing validation today. The risk is that the next
release-validation or migration feature must edit long mixed-purpose regions,
making behavior changes harder to distinguish from mechanical movement.

## First-Stage Scope

The first scoped PR for #96 should only publish this plan and link it from the
v0.5.0 maintenance scope. It should not close #96.

Goals:

- define staged refactor boundaries before code movement;
- keep the later PR sequence behavior-preserving by default;
- name the validation evidence and stop point for each stage;
- reserve a clear place for later zh-CN template validator coverage.

Non-goals:

- do not rewrite `scripts/validate-release.ps1`;
- do not change public CLI behavior or JSON/human output contracts;
- do not change validation pass/fail semantics or coverage strength;
- do not change project-bootstrap language migration behavior;
- do not mix this work with #118 old-release upgrade validation;
- do not create a release-candidate, tag, or publication finalization path.

## Staged PR Sequence

Each stage below should be a separate PR unless the maintainer explicitly
chooses a smaller or larger cut after reviewing the prior stage. Stages are
ordered to reduce review risk before moving behavior-heavy code.

| Stage | Goal | Primary files | Review boundary | Stop point |
| --- | --- | --- | --- | --- |

Read-only helpers extraction | Move source-inspection helpers behind a shared release-validation helper surface. | `scripts/validation/release-test-helper.ps1`, `scripts/validate-release.ps1` | Only read files, parse text, inspect Git output, or compare arrays. No fixture creation, scratch mutation, or CLI behavior change. | Stop when helper extraction is mechanical, check names/details stay stable, and full release validation passes. |

## Stage Details

### A. Read-Only Helpers Extraction

Candidate helper types:

- required-text assertions for documentation boundary checks;
- text match and allowlist inspection helpers;
- PowerShell parser and file encoding inspection helpers;
- Git file enumeration wrappers that return data but do not mutate state.

Expected validation:

```powershell
git diff --check
pwsh -NoProfile -File scripts/validate-release.ps1 -ScratchRoot <scratch-root>
```

Rollback boundary: revert the helper extraction commit or move the helper calls
back into `scripts/validate-release.ps1`. Because this stage is read-only, a
rollback should not need to repair generated fixtures or migration artifacts.

### B. Release Validation Check-Group Boundaries

Candidate groups:

- repository structure and public documentation boundaries;
- installer profile matrix and runtime smoke checks;
- memory upgrade and language migration fixtures;
- workflow-spec-lite validator fixtures;
- knowledge hub checks;
- parser, encoding, JSON, whitespace, and public safety scans;
- language policy and template checks.

Expected validation:

```powershell
git diff --check
pwsh -NoProfile -File scripts/validate-release.ps1 -ScratchRoot <scratch-root>
```

Rollback boundary: revert one check-group boundary at a time. A PR should not
mix group-boundary movement with new validation assertions unless that new
assertion is the explicit scope of the PR.

### C. Parser And Validator Fixture Helpers

The workflow-spec-lite validator coverage should move toward a fixture helper
surface before more validator cases are added. The first helper cut should
preserve the existing coverage:

- complete English spec fixture;
- bounded loop-contract spec fixture;
- zh-CN bilingual section fixture;
- zh-CN UTF-8 no-BOM fixture;
- negative fixtures for missing metadata, goals, non-goals, acceptance, risks,
  stop rule, and autonomy level.

Reserved space for future zh-CN template validator coverage:

- add future positive fixtures that are derived from the real zh-CN
  `spec-lite.md` and `tasks-lite.md` template shape;
- keep those fixtures public-safe and deterministic;
- keep fixture generation separate from validator behavior changes so template
  coverage can be reviewed independently.

Expected validation:

```powershell
git diff --check
pwsh -NoProfile -File skills/workflow-spec-lite/scripts/validate_spec.ps1 -SpecPath <fixture> -RequireExecutionContract -Json
pwsh -NoProfile -File scripts/validate-release.ps1 -ScratchRoot <scratch-root>
```

Rollback boundary: revert fixture helper movement without changing
`validate_spec.ps1` behavior. If a later PR changes the validator, it should
carry its own targeted positive and negative fixture evidence.

### D. Language Migration Mode Handler Split

The language migration script already has separable helper functions. The next
safe cut is to split command-mode dispatch into handler functions such as:

- `Invoke-LanguageMigrationAnalyze`;
- `Invoke-LanguageMigrationPlan`;
- `Invoke-LanguageMigrationApply`;
- `Invoke-LanguageMigrationValidate`;
- `Invoke-LanguageMigrationPlanNarrative`;
- `Invoke-LanguageMigrationApplyNarrative`;
- `Invoke-LanguageMigrationValidateNarrative`;
- `Write-LanguageMigrationHumanSummary`.

Expected validation:

```powershell
git diff --check
pwsh -NoProfile -File skills/project-bootstrap/scripts/language_migration.ps1 -ProjectDir <fixture-project> -Mode Analyze -SourceLanguage en -TargetLanguage zh-CN -Json
pwsh -NoProfile -File scripts/validate-release.ps1 -ScratchRoot <scratch-root>
```

Rollback boundary: revert mode-handler movement without changing the existing
mode names, required parameters, proposal-first behavior, backup-first behavior,
narrative proposal flow, JSON fields, or human summary wording.

## Cross-Stage Rules

- Keep public CLI behavior stable unless a future issue or PR explicitly scopes
  a behavior change.
- Keep every release-validation check at the same or stronger coverage level.
- Do not split a helper into an installed runtime dependency unless the helper
  is packaged for both copy-mode and link-mode installs.
- Do not combine modularization with release preparation, tag creation, or
  GitHub Release publication.
- Do not include local scratch paths, private overlay material, or local review
  evidence in public docs or PR bodies.

## PR Body Expectations

The first PR body should state:

- it is a behavior-preserving planning and boundary PR;
- it does not close #96;
- follow-up PRs should proceed in the Stage A through Stage D order unless the
  maintainer changes the sequence;
- validation evidence includes `git diff --check`, a PowerShell parser check,
  and full release validation.

Follow-up implementation PR bodies should add:

- the stage name;
- files moved or functions introduced;
- non-goals for that stage;
- expected validation and actual validation evidence;
- rollback and review boundary;
- whether the PR still leaves #96 open or closes the final remaining stage.
