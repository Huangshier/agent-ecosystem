# 项目术语表

## Summary

记录项目特有的术语、缩写、领域行话和易混淆概念。本文件是可选的；当
术语表有助于 agent 和协作者避免误解时创建。如果项目没有值得正式化的领域
专有词汇，可以删除本文件。

## Keywords

terminology, glossary, domain terms, abbreviations, project vocabulary

## 何时创建

在以下一种或多种情况适用时，术语表能增加价值：

- 项目所属领域术语密集（嵌入式系统、金融、医疗器械、协议设计、逆向工程）。
- 多个团队或外部协作者合作，对术语的使用存在差异。
- 代码库包含大量缩写、首字母缩略词或含义取决于上下文的多义词。
- 业务术语和技术术语重叠且容易混淆（如 HTTP "session" 与用户工作 "session"）。

## 何时不需要

以下情况可以跳过本文件：

- 项目规模小，术语在代码和文档中已足够清晰。
- 术语是标准的，已在框架或语言文档中有充分记录。
- 工作是短期或一次性的，没有长期协作者。

## 建议结构

保持表格精简。可根据项目需要增减列。

| 术语 | 定义 | 上下文 / 别名 | 备注 |
|------|------|---------------|------|
| *（示例）* Widget sync | 将 widget 存储与外部注册表定期对账 | 旧文档中也称 "widget refresh" | 生产环境每 5 分钟运行一次 |
| *（示例）* HAL | 硬件抽象层（Hardware Abstraction Layer） | 不要与 API 模块中的 "HAL"（HTTP Accept-Language）混淆 | 参见 `drivers/hal/` |

只填写与项目相关的行。添加真实条目后删除示例行。

## 建议

- 定义保持简短——一到两句话。
- `上下文 / 别名` 列用于交叉引用，不要写成长段落。
- 当术语有非显而易见的历史、弃用状态或已知坑点时，在 `备注` 列添加说明。
- Agent 通过 `## Keywords` 标题发现本文件，无需特殊路由配置。
- 术语变化时更新或删除条目。过时的定义比没有定义更有害。

## 说明

- 本模板完全可选。除非项目确实能从术语参考中获益，否则不要创建本文件。
- 不要把本文件当作变更日志或词汇表维护追踪器。它是活的参考文档，不是历史记录。
- 仅记录项目特有术语。不要添加编程语言或框架文档中已有定义的术语。
